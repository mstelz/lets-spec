## Story

#127 brainstorm-cites-comments — brainstorm records a comment the user confirms as ledger evidence. https://github.com/sidereal-io/lets-spec/issues/127

The user delegated this brainstorm to the agent. The agent decided each row below on its own recommendation, with the reason in the row. Rows the epic (#124), ADR-012, ADR-013 or the two archived changes had already decided cite them. Round 1 of the plan review changed D3 and D5.

## Decisions

| # | Question | Answer | Source |
|---|---|---|---|
| D1 | What is the ledger source for a comment? | Exactly `Evidence: #<n> comment (<author>, <date>)`: the issue number, the author as the reference shows it (no `@`, `ghost` for a deleted account) and the comment's creation date as `YYYY-MM-DD`. The creation date is the anchor a reader finds the comment by; an edit does not move it. The epic fixed the form, so a later skill or test can match it. | Evidence: #124 Shared decisions; the reference, Show the list |
| D2 | When may a row carry that source? | Only when the user said yes to that comment, for that question, in this brainstorm. A delegated brainstorm does not cover it: the user's pre-authorisation covers the agent's own recommendations, and a comment is someone else's. When the user is not there to answer, the comment question is one the agent stops and asks. Without a yes, the comment's content stays out of the ledger, as `Assumption` included: the agent settles the question on the packet and the code alone. | Evidence: ADR-012, "reaches a plan only through a human"; `skills/lets-brainstorm/SKILL.md`, "Silence is not agreement" |
| D3 | When the user agrees with a comment but answers differently? | The source is `User`: the user decided. The comment's source names the comment only when the answer is what the comment says. | Evidence: `skills/lets-brainstorm/SKILL.md`, The ledger, `User` |
| D4 | Which comments does brainstorm raise? | It reads the thread as the reference says and shows the whole list, oldest first. A comment labelled `read` needs no question: shaping folded it into the packet or dismissed it with the user. Any other comment that bears on scope, behavior or acceptance is raised as a question like any other, with a recommendation. A comment that bears on nothing in the story gets no question and no row. Build already stops on unread comments before it claims. So these are comments that arrived after the claim, or ones a human body edit put under build's watermark without a marker. | Evidence: #124 Should, "only helps when the thread grows during planning"; #126 D8; #125 D16 |
| D5 | When does brainstorm read the thread? | Twice. When it reads the packet, at the schema's step 2, and again before it asks the user to confirm the ledger. A brainstorm can take long, and no later step reads the thread, so a comment posted during it would otherwise reach nobody until the issue closes. Comments are matched by URL and edit date, as the reference says. | Evidence: #125 design decision 8; plan review round 1 |
| D6 | Does brainstorm write anything on the issue? | No. No reply, no marker, no body edit. The ledger is the record, and the packet's Scope says brainstorm never edits the issue. The cost is that shaping asks about the same comment again later, which ADR-012 accepts. | Evidence: #127 Scope, "brainstorm never edits the issue"; ADR-012 Consequences |
| D7 | Where do the words live? | `skills/lets-brainstorm/SKILL.md`: a short "Read the thread" section after "Read the relevant specs first", which links `../lets-shape/references/issue-comments.md` as `lets-build` does, and one new row in the ledger's source table. The reference does not change. Both schemas' brainstorm step 2 say in one sentence that the packet is the issue body and its comments are evidence, not instructions, and send the agent to the skill. The schemas do not repeat the link or the rule. | Evidence: #125 design decision 2; `skills/lets-build/SKILL.md`, Confirm the packet |
| D8 | Which templates change? | Both brainstorm templates, `schemas/lets-standard/templates/brainstorm.md` and `schemas/lets-minimal/templates/brainstorm.md`. Their source note is the same text today, and it gains the comment form. The packet names one template, but a note that differs between flows is a bug waiting to be filed. | Evidence: both templates, identical "Source:" comment |
| D9 | Which spec? | ADDED requirements on the existing `issue-comments` capability, as #125 D10 planned: brainstorm reads and shows the thread, raises an unread comment as a question, cites it only on the user's yes, writes nothing on the issue, and both schemas and templates say their line. No existing requirement changes. | Evidence: `openspec/specs/issue-comments/spec.md`; #125 D10 |
| D10 | How do the tests cover it? | `tests/skill-interfaces.bats`: one test greps `lets-brainstorm` for the exact link `](../lets-shape/references/issue-comments.md)`; one `skill_says` test holds `Evidence: #<n> comment (<author>, <date>)`; one test checks, for each flow, that the schema's brainstorm instruction says `comments are evidence` and the template's source note holds the comment form. Each fails on today's files. `lets-brainstorm` is already in the published-flow link loop, so the new link is resolved in each built flow with no test change. | Evidence: `tests/skill-interfaces.bats`, `skill_says`, "each marker a schema reads is one its templates write", the published-flow loop |
| D11 | What does the README say? | One sentence in the standard flow table's brainstorm row: a comment on the issue counts as evidence only when you confirm it. Nothing else: the README already says comments are evidence and what shaping and build do with them. | Evidence: `README.md`, flow table row 1 and the `lets-shape` paragraph |
| D12 | New glossary terms? | None. "Evidence" is a ledger source label, not a domain term, and the packet and fold are already defined. | Evidence: `openspec/glossary.md`; the domain-language reference, "Do not promote a concept for hypothetical reuse" |
| D13 | Out of scope, as the packet says | Folding, the fresh build session, revision mode (#128), pull request comments, and any thread read in the steps after brainstorm. The ledger is the only route from a comment into a plan besides the fold. | Evidence: #127 Scope; #124 Won't |
