## Story

#125 shape-folds-comments — shaping reads an issue's comments and folds the ones the user accepts into the packet. https://github.com/sidereal-io/lets-spec/issues/125

The user delegated this brainstorm to the agent. The agent decided each row below on its own recommendation, with the reason in the row, except where the epic (#124) had already decided it. Round 1 of the plan review changed D3 to D8 and added D14 to D17. Round 2 tightened D1, D3, D4, D6, D7, D12, D14 and D15.

## Decisions

| # | Question | Answer | Source |
|---|---|---|---|
| D1 | Which command fetches the thread? | One `gh api graphql` query on the issue: each comment's `url`, `author { __typename login }`, `authorAssociation`, `createdAt`, `lastEditedAt` and `body`, with `pageInfo` for paging, plus the issue's `lastEditedAt`. `gh issue view --json comments` has no bot flag. A REST path such as `gh api repos/...` fails the skill-interfaces test's `gh` check. `lastEditedAt` costs one field now and is the body's last edit that #126 needs. | Evidence: `tests/skill-interfaces.bats`, `gh api graphql` run on #102 |
| D2 | How is a comment labelled? | `candidate` when `authorAssociation` is OWNER, MEMBER or COLLABORATOR and the author is not a Bot; otherwise `outside`. A deleted account (`author` null) shows as `ghost` and is `outside`. The label is shown, never used to skip or hide a comment. | Evidence: #124 Shared decisions; GitHub GraphQL schema, `IssueComment.author` is nullable |
| D3 | What does the user see? | One numbered list, oldest first, one line per comment: its number, label, author, date and one sentence on what it says. Authors are written without `@`, and the sentence carries no `@mention`, so the list and the reply ping nobody. The whole list comes before any question, so the user sees the thread as a thread. | Assumption |
| D4 | Which comments get a question? | Every comment the newest read marker (D15) does not cover, in list order, one at a time, with a recommended answer: fold or dismiss in Shape one issue, take into the parent or dismiss in Ingest. Covered comments stay in the list, labelled `read`, with no question: shaping already judged them. A comment whose content is already in the packet is recommended as dismiss, with that reason. The questions run for every Kind, Chore included, as their own step after step 3 and before the template interview. An issue found by title search and confirmed is read like a named one. | Assumption |
| D5 | What does a fold write, and when? | A fold rewrites the packet lines the comment affects to say what is now true. It never pastes the comment's text. The edits ride the one body write Shape one issue already makes at its confirm step, so the user sees the folded body whole and says yes once. | Evidence: `skills/lets-shape/SKILL.md`, Shape one issue step 6 |
| D6 | What does the reply say? | Its first line is exactly `lets-shape read this thread.` Then one bullet per comment judged this run: `Folded:`, `Taken into #<parent>:` or `Dismissed:`, with the author without `@`, the date and what changed or why not. Posted with `gh issue comment <i> --body-file <file>`, never `--body`, because a summary of an untrusted comment can hold shell text. | Evidence: #124 Shared decisions (the reply is the audit trail) |
| D7 | When is the reply posted? | Only after the confirm step completes: the body is written in Shape one issue, the parent issue is created in Ingest, or the user confirms that an already-shaped packet stands unchanged. In that last case nothing is written and the Project fields stay as they are. A pass that stops earlier, at a size of L or XL or at a no, posts nothing. A run that judged no comment posts no reply. | Evidence: `skills/lets-shape/SKILL.md`, Shape one issue steps 5 and 6 |
| D8 | What happens to a comment on the input issue during Ingest? | The input is read-only, so nothing is folded there. A comment the user accepts is taken into the parent issue's Scope or Open questions, which Ingest writes anyway. The reply on the input issue lists it as `Taken into #<parent>:`. Only an edit to that issue's own body is a fold, as the glossary defines it. | Evidence: `skills/lets-shape/SKILL.md`, "The input is read-only"; `openspec/glossary.md`, Fold |
| D9 | Where does each rule live? | The reference `skills/lets-shape/references/issue-comments.md` holds the stance, the query, the labels, the list format, the read marker and the reply's shape. `SKILL.md` holds only the steps: when to read, ask, fold and reply. #126 and #127 then read the same reference. | Evidence: #124 Must, "one shared reference" |
| D10 | Which spec? | A new flat capability `issue-comments`, beside the other flat specs. #126 and #127 add their requirements to it. | Evidence: `openspec list --specs` layout |
| D11 | New glossary terms? | None beyond *packet* and *fold*, already imported. `candidate`, `outside` and `read` are labels in one reference; promoting them is reuse that has not happened yet. | Evidence: `openspec/glossary.md`, domain-language reference |
| D12 | How do the tests cover it? | `prose()` in `tests/skill-interfaces.bats` also lists `skills/*/references/*.md`, so every `gh` command in a reference is checked like one in a `SKILL.md`. New `skill_says`-style tests check that `lets-shape` links the reference, and that the reference holds the fixed first line, the three labels, `gh api graphql` and `gh issue comment` with `--body-file`. | Evidence: `tests/skill-interfaces.bats` |
| D13 | Out of scope, as the packet says | Build's stop on unread comments (#126), the brainstorm ledger row (#127), revision mode (#128), reactions, minimized comments and pull request review comments. | Evidence: #125 Scope, #124 Won't |
| D14 | What about a comment posted or edited during the interview? | After the confirm step, shaping always fetches the thread again, even when the first fetch found nothing unread. A comment the earlier fetch did not return, or whose `lastEditedAt` changed, is shown and asked about like the others. Shaping then confirms the updated body and writes it with `gh issue edit`, on the issue in Shape one issue or on the parent in Ingest, and fetches again until nothing is new. The reply then lists every comment it judged, and no comment is marked read unseen. Comments are matched by URL and edit date, never by the local clock. | Assumption |
| D15 | What counts as a read marker, and what does it cover? | A comment whose first line is exactly `lets-shape read this thread.` and whose author would be labelled `candidate`. It covers every earlier comment not edited after it, and every marker. A comment edited after the newest marker is asked about again. An `outside` or bot comment with that line is shown like any other comment and marks nothing. The marker's own comment is never asked about. | Evidence: #124 Shared decisions; the forgery and edit scenarios from review rounds 1 and 2 |
| D16 | Does a human body edit count as read, for shaping? | No. Shaping's cutoff is the newest read marker only. A human who edits the body has not judged the thread. Build's watermark is #126's to define. | Assumption |
| D17 | One name for the mode? | The artifacts say *Shape one issue*, as `SKILL.md` names it. | Evidence: `skills/lets-shape/SKILL.md` |
